# S7：同步节点推进中断的检测与安全恢复

## 目标与范围

同步插件完成后，引擎通常在同一个 worker 内继续下一节点，不经过消息队列。进程退出、阻塞或输出处理异常，可能留下“节点 FINISHED，进程仍醒着，下一节点未启动”。它与 S1（异步调度完成后的执行消息未推进）分开编号为 S7，类型 `sync_advance_stalled`。

本次实现检测、受限安全恢复和 DevCloud 验证。不承诺任意业务副作用恰好一次，不根据页面绿色状态直接重跑插件。现有 S1–S6 行为保持兼容。

## 安全依据

现有顺序是：插件返回成功 → State FINISHED → 输出提取 → 保存执行数据 → 同一 worker 推进。因此 FINISHED 本身不能证明输出完整。新增检查点位于 handler 成功返回之后、进入下一轮循环之前，输出已保存才可记录。

采用每个 Process 最多一条 `SyncAdvanceCheckpoint`，包含源节点、源版本、目标节点、阶段和记录时间。阶段为 READY、CLAIMED、RELEASED；相同源节点版本的阶段只能单向变化，不能被旧 worker 重新置为 READY。

1. 正常 worker 在输出保存后写 READY；继续推进前，锁定 Process 和检查点，重新核对当前节点、版本、暂停/冻结/结束状态，竞争 READY → CLAIMED。竞争失败立即退出，不执行后继、不修改新执行者的睡眠状态。
2. 恢复在事务中核对根流程、源状态版本、唯一后继、无当前版本 Schedule、无跳过/忽略错误、静默时间以及检查点 READY，竞争 READY → RELEASED，同时令 Process 休眠。两项更新同一事务提交。
3. 事务提交后，补发后继 execute，带现有源节点/版本令牌。晚到旧 worker 的 CLAIMED 竞争失败；重复补发由原有执行令牌限制。
4. 如果补发失败或消息再次丢失，RELEASED + Process 仍在源节点休眠可以再次补发。S7 保留此形态，S1 不重复立案。
5. 正常推进的 CLAIMED 不能被恢复抢占。下一同步节点可更新这一行；旧节点版本无法恢复过期检查点。新运行时通过 ORM 删除 Process 时连带删除检查点，不按节点无限累积。数据库不设外键约束（db_constraint=False），旧运行时回退后仍可清理 Process；旧运行时或直接 SQL 删除可能留下孤立检查点，后续升级清理时核查，不能按年龄误删仍在使用的记录。

检查点写入/竞争异常不能降级绕过：保留现场，按既有中断处理或报错。默认关闭新增正常路径写入。携带 running_node_version 的数据库中断重试，在唤醒进程之前核对检查点；同一源节点/版本已有检查点时拒绝重入，避免晚到的旧恢复路径唤醒已交出的进程。

## 检测与禁止恢复的边界

快档扫描在独立开关开启后包括存活的清醒进程。根流程 RUNNING、ServiceActivity FINISHED、静默超阈值、无当前版本 Schedule，形成 S7 候选；没有匹配检查点时还要求完成晚于该轮心跳。暂停、冻结、回滚保留节点不纳入。二次确认与现有游标窗口复用。写入 READY 时刷新 Process.last_heartbeat，避免同步插件运行很久而错过增量扫描窗口；在检查点之前中断的历史任务仍需显式回扫。

无检查点、检查点 CLAIMED、源版本/目标不符、跳过或忽略错误、根流程结束/暂停、进程已推进等均禁止恢复。缺少检查点的历史任务只能确认“疑似同步推进中断”，需要人工核对输出和原 worker；不能由脚本伪造 READY。原 worker 已 CLAIMED 但未进入下一轮就崩溃的极窄间隙同样转人工，不能用超时推断其已失去执行权。

该方案优先保守接管，避免引入覆盖整个执行期间的租约/心跳和业务幂等改造，也不把所有同步节点改成异步消息交接。

## 开关、上线与回退

- `bamboo_engine.config.Settings.SYNC_ADVANCE_CHECKPOINT_ENABLED=False`：正常同步路径检查点。
- `PIPELINE_DIAGNOSTICS_SYNC_ADVANCE_ENABLED=False`：S7 扫描及恢复。
- 仍需现有恢复 apply、类型白名单、项目范围、熔断/次数限制；S7 不允许通过“确认风险”绕过发送/执行令牌开关。
- 先迁移新表，再升级全部相关 worker，最后开启检查点、检测；先 preview 后小范围 apply。旧 worker 不认识检查点，因此混部期间禁止 S7 恢复。
- 关闭检查点开关时，已有 READY/RELEASED 记录仍须由支持竞争协议的 worker 处理；应先关闭 S7 apply，等在途任务退出后再退回旧 worker，不删除现场记录。
- 每个同步节点增加检查点写入与竞争事务。必须单独评估生产 DB 吞吐；DevCloud 功能测试不能替代生产容量验证。

## 验收

在独立 DevCloud 环境使用真实 DB、RabbitMQ、Celery worker 和标准运维任务页面。每个恢复场景另建任务；原卡住样本不恢复。故障注入只暂停/终止真实执行路径，不手工构造 FINISHED/Process 状态。

覆盖：READY 后中断并恢复、原 worker 迟到、补发消息丢失后再恢复、输出未保存无检查点时拒绝恢复、CLAIMED 后中断拒绝抢占、默认关闭正常任务、输出传递与前后节点执行次数。保留卡住和恢复任务、原始页面链接、截图、状态及执行次数证据，并回归 S1–S6 相关测试。
